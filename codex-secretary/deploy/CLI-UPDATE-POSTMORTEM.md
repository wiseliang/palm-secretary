# CLI 更新故障复盘（2026-10-20）

## 证据与原因

10 月 14 日 history-0.17.2 和 10 月 20 日 direct-0.17.3 均在脚本第二行报
`set: pipefail\r: invalid option name`。脚本以 CRLF 发布，失败发生在下载之前。
上次只修复当时 release 的字节，并添加未纳入所有发布入口的 Git 属性；后续
release 又复制了旧脚本。只运行现有版本的脚本没有覆盖真实 HTTP 更新链路。

初版还存在：版本检查期间未持锁、安装期间可提交任务、切换后启动失败未恢复
旧代理、没有旧 CLI 包保留策略。此前“失败保留原版本”的描述只适用于安装前半段。

## 修复及验收

后端读取脚本后移除 BOM、统一 CRLF/CR 为 LF，通过 bash -c 执行；版本作为独立
参数传入，不插值到脚本。Git 的 *.sh eol=lf 和换行测试作为第二层保障。
更新检查前持锁，提交任务前再次检查锁；验证失败原子恢复旧代理并重启 bridge。

2026-10-20 使用短时本地管理员测试会话调用真实 POST /api/codex/update，返回 200，
0.162.1 -> 0.163.0，bridge 初始化及实际代理版本验证通过；测试会话随即注销。
验收特意保留 CRLF 输入，验证运行时兼容而非仅修补文件。

## 空间保留策略

仅在新版本启动且版本复核成功后清理专用 packages/npm 目录；保留当前版本与
升级前版本，跳过正在执行的版本。只删除普通、精确数字版本名目录；符号链接
及非版本目录不动。清理失败不撤销成功升级。旧版本可从 npm 重新安装。
此次原本仅有 0.162.1，升级后保留两版，实际删除数为 0。

## 后续发布检查

发布时包含 server/cli-update.ts，执行 build:server、test:cli-update 和 Linux 上
node tests/cli-cleanup.mjs；确认编译产物调用 loadUpdateScript，而非直接执行文件。
真实有新版本时验收 HTTP 更新响应、bridge、代理版本、保留目录和服务健康。
不得仅凭 bash -n 或 /api/health 宣称完整更新通过。
